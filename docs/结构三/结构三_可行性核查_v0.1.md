# 结构三第一步可行性核查

日期：2026-08-18
结论：**上一版推荐的起点（扩 PersONAL）不可行，起点改为 FindingDory。改后可行，且不需要模拟器。**

---

## 1. 硬件与环境实测

| 环境 | 实测 | 判定 |
|---|---|---|
| 你的 Mac | MacBook Air, Apple Silicon (darwin/arm64)，磁盘 **461 GB 总 / 222 GB 空闲** | 磁盘充足；**无独显** |
| Cowork 本地 VM | Linux, Python 3.10, 有 git/ffmpeg，**无网络**，磁盘仅 4.2 GB 可用 | 只能做本地文件处理，不能下载 |
| 本会话云容器 | 2 核 / 7 GB 内存 / **无 GPU** / 30 GB 可用 | 不能承载 32.5 GB 数据集与视觉模型 |

---

## 2. 阻断项：Habitat 跑不了

habitat-sim 官方文档明确：headless 安装依赖 **EGL**，而 EGL **does not work on MacOS**。

叠加你的 Mac 无独显、云容器无 GPU，结论是：

> **任何需要实时运行 Habitat 模拟器的方案，在你现有条件下都不可行。**

这不是性能问题，是平台不支持。

---

## 3. PersONAL 起点的两个致命问题

上一版方案让你从 PersONAL 起步，核查后**撤回这个建议**：

1. **代码未公开可得。** 论文里给的是 `github.io/PersONAL` —— 一个残缺的占位链接，没有域名前缀。多轮检索没有找到可用仓库或项目页。
2. **两个任务都必须跑模拟器。** PAN 需要 500 步在线导航；POG 需要 2500 步在线预探索来建图。没有离线数据发布。

也就是说，即使你有 GPU，也还得先等作者放代码。

---

## 4. 正确起点：FindingDory

核查结果全部有利：

| 项目 | 状态 |
|---|---|
| 代码 | **真实公开**：`findingdory-benchmark/findingdory-habitat` 与 `findingdory-train`，有项目页，README 可访问 |
| 数据 | **HuggingFace `yali30/findingdory`，32.5 GB，85,083 行**（train 79.2k / val 5.87k） |
| 数据形态 | **预渲染视频 + parquet 标注**，含 episode ID、视频路径、问题、答案帧索引、任务分类 |
| 是否需要模拟器 | **不需要**。论文原文：交互阶段 agent 拿到的是 recorded history（images, pose, past actions），离线评测 |
| 降级版本 | 提供 **96 帧下采样版**，用于降低算力 |
| 规格 | 640×480 RGB-D；每 episode 400–3500 帧；2–11 次 pick-and-place |
| 磁盘 | 32.5 GB vs 你的 222 GB 空闲 —— **装得下** |

**为什么它比 PersONAL 更适合你：**

1. **绕开 macOS 的 EGL 死结**——数据是预渲染的，不碰模拟器
2. **它已经有"物体被移动"的时序结构**，这正是 PersONAL 缺失、而你结构三最需要的
3. **人物归属可以从数据里推导**：pick-and-place 是脚本化的，"什么时候、哪个物体、从哪到哪"在标注里，把这些事件重新归因给虚构的家庭成员是可控的合成注入

---

## 5. 必须诚实说明的三个限制

1. **FindingDory 是单 agent，没有"人"的概念。** 你把 scripted agent 的 pick-and-place 重新解释为家庭成员活动，这是 **semi-synthetic**，论文里必须明说，不能包装成真实多人数据。
2. **离线的是"数据"，不是"模型"。** 基线用 Qwen2.5VL 一类的 VLM，推理仍然需要 GPU。你的 Mac 做不了这一步。
3. **32.5 GB 在国内下载可能很慢。** 建议走 HF 镜像（`hf-mirror.com`），或先只下标注。

第一步（见 §7）**不需要 GPU**。真正需要 GPU 的是跑 VLM 基线，那时候再租：

## 7. 今天就能做、且零成本的可行性验证

**先只下 parquet 标注，不下视频。**

标注文件相比 32.5 GB 的视频极小，几分钟能拿到。要验证的唯一问题是：

> **pick-and-place 事件的标注结构，是否足以支撑"谁在什么时候把什么从哪移到哪"的推导？**

具体检查清单：

1. 每个 episode 的交互事件是否带**时间戳/帧索引**
2. 是否能取到**物体 ID**（而不只是类别）
3. 是否有**起止位置**（房间 / 家具 / 坐标）
4. 同一物体在一个 episode 内是否会**被移动多次**
5. 不同 episode 之间，场景是否**延续**（这决定了能不能做跨天/跨 session 的记忆实验）

**如果 1–3 满足**：整个计划成立，往下走。
**如果只满足 1–2**：人物归属只能挂在"事件"而不是"位置转移"上，你的 `TRANSITION_SURVIVAL` 模型要改设计。
**如果 4 不满足**：没有"物体反复移动"就做不了生存模型，需要换数据或自己扩充。
**如果 5 不满足**：跨 session 记忆实验做不了，结构三的长期部分要降级。

这一步的价值在于：**它用几乎零成本，决定了后面三个月的方向是否成立。**
