## 2. 第一轮发现的修复

### F-1 评价产物与代码零绑定 → 已修

新增 `EvaluationProvenance`，全部字段都是**测量值**而非声明值：

```python
class EvaluationProvenance(ContractModel):
    code_version: str                    # git:<sha> 或 git:<sha>+dirty
    source_tree_sha256: str              # 测自 src/ apps/ benchmarks/ pyproject.toml
    evaluator_module_sha256: str         # 测自 evaluator.py 本体
    working_tree_clean: bool | None      # None = 未知
```

它进入 `evaluation_run_identity`，因此**改动评价代码必然改变 run_id**。

`EvaluationRunner.evaluate()` 内部强制测量；若调用方传入的 `provenance` 与实测不符则拒绝执行。

**攻击复验：**

```

修复后：篡改指标计算 →
  evaluator_module_sha256  9a95ef3d… → b68f0845…   已变
  evaluation_run_id        b5611dd6… → fd9a4236…   已变
  recall                   1.0 → 0.5
```

## 3. 第二轮：攻击我自己的修复

### A-1 [根本限制] 报告无法自我认证 → 记录并提供审稿人侧检查

**攻击**：伪造 provenance，按新的公式重算 `evaluation_run_id`、`metric_id`、`evaluation_report_sha256`。

**结果**：伪造报告**通过全部内部校验**，声称 `code_version: git:000…0`，recall 0.99。

**这不是校验问题，是签名问题。** 自哈希只能证明内部一致，不能证明来源。彻底解决需要签名或外部不可变登记，超出本轮范围。

**已做的**：新增 `EvaluationProvenance.verify_against(repository_root)`——审稿人侧对照检出的检查：

```
verify_against 拒绝 : reported source_tree_sha256 does not match the checked-out tree
```

并写成测试 `test_a_self_consistent_report_cannot_authenticate_its_own_provenance`，**把残余限制固化为一条会一直存在的测试**，而不是一句文档里的免责声明。

### A-2 [我引入的缺陷] 无 git 时谎称干净 → 已修

我的第一版：

```python
except RuntimeProvenanceError:
    code_version = "unversioned:no-git"
    working_tree_clean = not code_version.endswith("+dirty")   # → True
```

**没有 git 就无从知道工作树状态，却报告 clean。** 这正是我在第一轮批评 F0 的同一类错误：把"未知"折叠成"良好"。

**已修**：`working_tree_clean: bool | None`，未知时为 `None`。

```
code_version       : unversioned:no-git
working_tree_clean : None
```

### A-3 [我引入的缺陷] 两字段可互相矛盾 → 已修

手工构造 `code_version="git:…+dirty"` 配 `working_tree_clean=True` 原本被接受。已加跨字段验证器：

```
git:0000…+dirty      clean=True  -> 拒绝: working_tree_clean contradicts the recorded code_version
git:0000…            clean=False -> 拒绝: working_tree_clean contradicts the recorded code_version
unversioned:no-git   clean=True  -> 拒绝: an unversioned tree cannot claim a known working-tree state
```


**唯一失败项是既有问题，与本次修改无关**，我用 `git stash` 验证过：

```
tests/test_direction_three_grounded_search.py::test_full_top_k_tolerates_machine_epsilon_probability_overshoot
assert 0.9999999999999999 > 1.0
```

该测试断言浮点求和**必然溢出** 1.0。这依赖 IEEE-754 的求和顺序与平台：你的 Python 3.13/arm64 上溢出，我的 3.11/x86_64 上不溢出。

**这本身是第七项发现**：一个断言"浮点必然向上溢出"的测试不可移植，复审者换平台就会看到失败——而 F0 的整个主题就是可复现性。建议改为断言 `posterior_mass_returned <= 1.0` 且 `abs(sum - 1.0) < 1e-9`，即"容忍机器精度"，而不是"要求溢出"。**我没有改它**，因为它属于结构三而非 F0 范围。
