## 三个系统性阻塞

### 1. 原始相机初始化位置与引擎实际位置有稳定差异

全部房屋原始 agent y 为 `0.95`。CreateHouse 后，index1–11 的 SDK agent y 为 `0.9009997844696045`，index12 为 `0.9010000228881836`，下降约 4.9 cm；观察到的起点 x/z、航向保持，俯仰约为 `30.000003814697266`，接近原始 30 度。此位置差异超过当前 1 mm 原始 agent 位置门槛，因而在第一条 SDK 记录就拒绝。

这说明必须核对引擎初始化语义；不能直接扩大容差后宣布通过。原始请求、自位姿实际回执、初始化后的旋转轨迹，应分别保留并核验。当前失败记录不可回写成通过。

### 2. SDK 的无资产对象普遍存在，当前完整资产审计会关闭全局资格

12 屋共 1,618 个 SDK 目录实例。其中 946 个是原始 `objects/children` 实例，全部按完整 ID 找到且 assetId 完全相符：没有原始实例缺失、没有资产错配。

额外实例包括 78 个具有 assetId 的门窗对象：38 个 Window、35 个 Doorway、5 个 Doorframe。这些对象应和源房屋的完整建筑资产清单核对，不能只检查 objects。

另有 594 个 SDK 实例的 assetId 为空：358 个 Wall、57 个 Floor、88 个 Shelf、75 个 Drawer、10 个 SinkBasin、6 个 DiningTable。其中 179 个派生部件的名称前缀可对应有资产的父对象，415 个是程序生成墙／地板。这只是诊断线索，名称关系尚不能授权继承父资产身份。

按照当前 `unknown_runtime_assets_prevent_complete_exposure_audit` 规则，任何一个未知资产都会关闭整批资格。因此即使相机门槛被有证据地修复，仍不能导出监督数据。应补充可追溯的生成几何／派生部件来源和隔离规则；不能简单忽略这些实例，或凭类别／名称填入资产 ID。

### 3. 源 JSON 的 position 不能直接等同于 SDK transform position

全部 946 个源实例的源 position 与 SDK transform position 的距离都大于当前 1 mm 门槛：最小 1.186 mm，中位数 82.372 mm，90 分位 458.776 mm，最大 2.015 m。这并不证明 946 个物体都发生了物理运动。

多个家具的源 position 接近 SDK AABB center，而非 transform pivot。例如 index2 的 Bed：

| 坐标定义 | x | y | z |
|---|---:|---:|---:|
| 源 JSON position | 0.607128108 | 0.337122947 | 1.034501696 |
| SDK transform position | 0.607128084 | 0.009132892 | 1.037434220 |
| SDK AABB center | 0.607128084 | 0.337122917 | 1.034501672 |

329 个源 `kinematic=true` 实例中，286 个源 position 到 SDK AABB center 小于等于 1 mm；该组 AABB 残差中位数约 0.000916 mm。617 个 `kinematic=false` 实例中，59 个小于等于 1 mm，AABB 残差中位数约 5.115 mm。后者可能包含引擎初始化沉降、中心定义变化等因素，当前记录不足以单独归因。

必须明确训练位置标签究竟是 transform、AABB center 还是其他定义，并分别记录源放置请求与实际初始化状态；不能默认二者一致，也不能把框内表面点当成该中心。

## 建议的紧邻主线工作

先依据引擎源码或独立受控实验，明确 CreateHouse 的 agent 高度和对象位置语义，建立从原始请求到 SDK 实际状态的可审计记录；保留本批失败原件。再完成程序生成几何与派生部件的资产来源审计，处理真实运行时资产隔离。两个问题均解决后，才对这批固定房屋重新形成监督导出资格和实际可见目标清单，继续实例／位置观测因子的离线训练和校准。

本报告没有调整现有先验、任务效用、成功阈值或研究范围。
