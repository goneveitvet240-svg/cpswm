## 分阶段实现

1. **失败回执先修**：在替换主 controller 前执行请求/场景校验；确保任何初始化错误都写入最终用于返回 metadata 的 controller/manager 状态。为 guard 路径加入实际 build 的正反对照，证明不再出现“失败却成功”。这一步不创造额外角色。
2. **房屋生命周期**：主 agent 初始化 → CreateHouse 成功 → 物理/导航/出生点就绪 → 新的 post-house spawn 入口。入口名及实现待代码落地，当前 SDK 无此能力，不输出假装可执行的 SpawnActor 命令。
3. **角色生成事务**：检查数量、出生点可达与碰撞体间距、唯一角色 ID、可见身体与独立摄像机/控制器/持物状态；全部成功后再发布完整 roster。失败不得继续采集；若无法可靠回滚，明确废弃 episode，而不是伪装恢复成功。
4. **状态机**：绑定房屋 generation；相同请求幂等，不多生成；过期请求拒绝；成功建房后不得由旧 Initialize 清空角色；reset 必须开始新 generation。不同 agent 的动作、相机和观测序号不能互串。
5. **真实人物层另验收**：多个胶囊 robot agent 只证明底层多实体能力。正式人物执行还需要许可明确的可渲染人物资产、拿取/携带/交接/放置的真实连续物理后果、遮挡与实例跟踪。不能用颜色 ID 真值、对象瞬移或手填角色标签替代。

## 构建后两轮验收矩阵

第一轮：1/2/目标规模角色合法正例；空/碰撞/不足出生点；部分生成失败；全部角色初始化响应；逐角色动作隔离、相机/图像/持物归属；普通场景回归。

第二轮：重复/迟到生成请求、房屋跨代重放、半失败后重试、重新初始化导致角色丢失、原始 metadata 与解码错配、动作后异常与停止采集。含成功完整链，不能只验证拒绝负例。

通过底层后，再另立真实人物与结构二连续历史验收：旧解释 → 可见迟到反证 → 后缀重算 → 账本撤回/新增 → 后验/动作变化。上述数据门与模型/状态/预算未明确前，training_ready=false、training_started=false。
