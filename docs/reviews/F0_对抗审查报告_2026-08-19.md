## 2. 发现（按严重度）

### F-1 [P0] 评价产物与代码之间零绑定 —— 这是主因

**事实：**

`EvaluationReport` 的全部字段里，与"谁算出了这个数"有关的只有一个：

```python
evaluator_version: str = "f0-evaluator@0.9"
```

而它的赋值是：

```python
evaluator_version = EvaluationReport.model_fields["evaluator_version"].default
```

即**从模型字段的默认值里把这个字面量取出来，再写回报告**。它不是任何东西的度量。

`apps/evaluation_runner/run_f0_vertical_slice.py` 全程**没有调用** `build_version_bundle`，也没有产生 `ReplayManifest`。

**攻击验证：**

把 evaluator 的指标计算改成对所有 recall 返回 0.5，重跑 CLI：

```
evaluator_version        : f0-evaluator@0.9        <-- 未变
evaluation_report_sha256 : 92ff549cbc058411…       <-- 已变，但自洽
failure_reasons          : []
  controlled_observation_recall   value=0.5
  anomaly_observation_recall      value=0.5
```

再把这份报告喂回 `EvaluationReport.model_validate_json`：

```
完整契约重新验证通过 : True
```

`evaluation_run_id`、self-hash、metric binding、leakage flag **全部通过**。

**为什么这是 BLOCK 级：** 复审者手里只有报告。报告里没有任何字段能让他判断这份报告是由哪一版评价代码产生的。而 F0 的整个目的就是"可比、可复现的评价身份"。这与阻断清单里已有的 **"P0 运行身份未绑定内容"** 是同一类问题——A0 侧做了，F0 侧漏了。

**修复方向：** `EvaluationRunner.evaluate` 接受一个 `VersionBundle`（或至少 `code_version` + `source_tree_sha256`），写进 `EvaluationReport` 并纳入 `evaluation_run_id` 与 self-hash。`evaluator_version` 从字面量改为由源码内容派生。

### F-2 [P0] `git_head_code_version` 不检测脏工作树

**事实：** `provenance.py` 只跑 `git rev-parse HEAD`，不检查 `git status --porcelain`。

**攻击验证：**

```
clean  code_version      : git:3f6880c2578419e478d4b567ebbc31ab80cb0257
clean  source_tree_sha256: f3a943e68e0c3b71…

[在 src/ 下追加一行]

dirty  code_version      : git:3f6880c2578419e478d4b567ebbc31ab80cb0257   <-- 未变
dirty  source_tree_sha256: 246323f187cac30e…                             <-- 已变
git status --porcelain 非空 : True
```

**为什么现在特别要命：** 你的仓库**此刻就是脏的**——7 个未提交文件，其中三个在 `src/`：

```
 M src/cpswm/foundation/runtime_orchestration/replay.py            ← A0 P0 区域
 M src/cpswm/system/world_model_simulator/symbolic.py              ← F0 P0 真值泄漏区域
 M src/cpswm/system/counterfactual_event_hypergraph/contracts.py   ← CHEH P1 区域
 M tests/test_f0_long_horizon_vertical_slice.py                    ← F0 测试文件本身
```

（内容是 ruff 的 `zip(strict=)` / `ClassVar` / 删未用变量等 lint 修复，非逻辑变更——但机制上无从区分。）

所以**当前工作树里产出的任何 A0 artifact，都会宣称一个它并不处于的 commit**。复审者按该 commit 检出后 `source_tree_sha256` 对不上，而报告里没有任何字段告诉他"这是脏树跑的"，他只能看到一个无法归因的 mismatch。

**修复方向：** `git_head_code_version` 增加 `git status --porcelain` 检查；脏树时返回 `git:<sha>+dirty` 或直接抛 `RuntimeProvenanceError`。至少必须在 `VersionBundle` 里显式记录 dirty 标志。

### F-3 [P0] `source_tree_sha256` 不覆盖 `apps/` 与 `benchmarks/`

**事实：**

```python
candidates = list((root / "src").rglob("*.py"))
pyproject = root / "pyproject.toml"
```

只有 `src/**/*.py` + `pyproject.toml`。

**攻击验证：**

```
修改 apps/evaluation_runner/run_f0_vertical_slice.py  +  benchmarks/…manifest_v0.4.json
source_tree_sha256 changed : False
```

**为什么是 P0：**

1. 复审文档里被引作证据的 CLI 输出哈希，正是 `apps/evaluation_runner/run_f0_vertical_slice.py` 与 `apps/direction_three/*.py` 产生的——**这些脚本不在 provenance 覆盖内**
2. 文档 §4 称"版本库内的 checked-in manifest 视为可信 benchmark authority"，而这些资产在 `benchmarks/` 下——**同样不在覆盖内**。我全仓搜索确认：`src/` 里**没有任何一处**引用 `benchmarks/`
3. `--benchmark-dir` 是可在命令行覆盖的参数，而报告里**不记录实际使用的目录**

于是"可信权威锚"的信任链是循环的：manifest 之所以可信是因为它在仓库里 → 但没有任何东西绑定仓库状态 → 所以没有任何东西绑定 manifest。

**修复方向：** `source_tree_sha256` 扩展到 `apps/`、`benchmarks/`（或单独增加 `asset_tree_sha256`），并把实际 `benchmark_dir` 的解析路径与内容哈希写进报告。

### F-4 [P1] `model_versions` 是自我验证，从不与现实比对

**事实：** `verify_replay_provenance` 里：

```python
actual = build_version_bundle(
    repository_root,
    configuration=active_configuration,
    model_versions=runtime_versions.model_versions,   # ← 用调用方自己的值构造 "actual"
)
if runtime_versions != actual: ...
```

`actual.model_versions` 恒等于 `runtime_versions.model_versions`，该字段上的比较**永远不可能失败**。随后只检查 `manifest.model_versions == runtime_versions.model_versions`，而两者都由调用方提供。

**攻击验证：**

```
verify_replay_provenance PASSED : True
accepted model_versions         : {'detector': 'grounding-dino@99.9-NEVER-EXISTED',
                                   'llm': 'gpt-fictional@0'}
```

现有测试 `test_replay_rejects_manifest_runtime_and_input_mismatches` 只覆盖 manifest 与 runtime 不一致，没有覆盖"两者一致但都是编造的"。

**为什么现在优先级尚可控：** 当前 F0 没有真实感知模型，`model_versions` 实际内容为空/占位。但阻断清单里写的是"核验实际 Git HEAD、源码树哈希、活动配置、**模型版本**"——这一项目前并未成立。到 S3-3 接入真实 VLM 时会立刻变成 P0。

**修复方向：** 要么引入可信 model registry 并与之比对，要么把 `model_versions` 明确降级为**自声明字段**，从"已核验"清单里移除，避免宣称超出实现。

### F-6 [P1] 文档自陈的两处未闭合，直接违反 M03/M16 核心原则

文档 §4 自己写了：

> **"outcome model version/domain 目前只在未持久化的执行包中校验，canonical log 单独不能重建该瞬时绑定。"**

这与「**派生投影必须可从规范日志重建**」正面冲突。如果某个绑定只存在于一个不落盘的对象里，那么规范日志就不是完备的重建来源——M16 的可重建性主张出现缺口。

> **"active verification 阶段的 `observation_opportunity_id` 仍只是 observation 内记录，尚未绑定完整 opportunity envelope。"**

这削弱了结构三 §9.1 的 `not_found` 负证据链：要求 `not_found` 必须绑定真实观察机会，但事后只能拿到一个 ID，无法核验该机会当时的视野/遮挡/距离参数。

**这两条都被写在"信任边界"一节里，读起来像是范围声明；但它们不是威胁模型的取舍，是核心不变量的缺口。** 复审者会区分这两类，而当前文档把它们混在同一节里。

**修复方向：** 从"信任边界"移到"已知未闭合阻断项"，各自给出可执行的关闭条件。
