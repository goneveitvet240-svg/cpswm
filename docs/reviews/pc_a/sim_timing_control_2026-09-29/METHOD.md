# 如何解释本轮时序实验

本批实际功能源码冻结后，先依次运行两轮 A 自审，再运行预先固定的完整矩阵。它核查的是环境采集条件，不更新神经模型，不修改正式观测似然或行动方法。

每次场景创建后保留 34 个 SDK 事件：初始状态、一次准备、16 组“时钟调用＋实际 Pass”。公共记录只有 16 个真实 Pass 的 RGB 和执行状态；其余事件全部用于私有诊断。三个条件都具有相同调用数，但动作种类与耗时不同，不能把“调用次数相同”说成“所有渲染及壁钟时间相同”。初始创建过程尚未被此控制器干预。

| 条件 | 准备调用 | 每次观测前的时钟调用 | 最终公共动作 |
|---|---|---|---|
| auto | Pass | Pass | Pass |
| frozen | PausePhysicsAutoSim | Pass | Pass |
| stepped | PausePhysicsAutoSim | AdvancePhysicsStep，0.01 秒 | Pass |

成功返回的调用保存请求参数、实际 lastAction/lastActionSuccess、拥有者命令 ID、RGB、掩膜和完整对象位姿。SDK 事件与公共记录逐字绑定；任何失败均不返回成功观测。对同一个 action ID 不重发，准备不可重复，16 次之外的请求拒绝。SDK 返回明确失败状态时会保留该事件；若在 SDK 解码时直接抛异常，则保存错误栈和此前完成的前缀，没有合法的该次 Event，不能伪造完整响应记录或声明实现了故障恢复。

“暂停有效”看准备后每次实际物体位姿变化，不仅看 isSceneAtRest。该标志受物理暂停影响，并不代表现实物体已经达到自然平衡。“步进 0.16 秒”只指 16 个 0.01 秒请求成功返回，不测量创建阶段或引擎内部未暴露的全部时间。工具中的 geometry_since_pause 对三个条件均指准备后的参考态；auto 的参考态实际是准备 Pass，不是暂停。

完整保存 16 帧，同时固定报告后 8 帧的逐字 RGB/掩膜一致性和位姿变化。它们是诊断窗口，没有事后寻找最好的截止点。逐字一致只证明此序列中的重现性，不意味着分类正确、物理合理性已全面认证、跨重置必然相同或多场景泛化。候选框与目标框 IoU>0 仍仅表示描述性重叠，不给候选授权人物/物体身份。

320/640 指相机原始图像尺寸；两个前端各自的原有内部预处理、权重及 0.5 开发过滤值保持不变。更大的相机图像不等于直接将模型内部张量尺寸改为同一数值，过滤值也不是已标定的目标存在概率阈值。本批只测量采集条件，不声称改善模型。

如果冻结物理后图像仍变化，证据只能说明已记录对象位姿变化不是该图像变化的必要条件；曝光、渲染状态、未记录状态或其他机制尚需专门干预。若图像稳定但持续漏检，问题已经独立于当前帧间不稳定，后续应检查可信实例对应和前端可见性，而不是用未经标定的负观测更新掩盖漏检。

官方依据：[AI2-THOR 初始化/物理时间接口](https://ai2thor.allenai.org/ithor/documentation/initialization/)；本机 ai2thor 5.0.0 的 Controller.multi_step_physics 亦实际使用先暂停再 AdvancePhysicsStep 的顺序。外部文档提供接口语义，实际效果以本轮源码绑定的 SDK 事件、原图与位姿记录为准。
