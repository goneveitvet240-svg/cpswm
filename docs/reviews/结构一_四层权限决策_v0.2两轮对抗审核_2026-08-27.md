# 结构一四层权限决策 v0.2：两轮对抗审核

日期：2026-08-27  
审核对象：四层放置语义、权限来源、撤销链、两个直接对手及开发统计  
最终状态：`development_survived_adversarial_audit`，不是论文证据

## 审核底线

本审核不问“模块是否存在”，只问五件事：攻击者能否伪造权限、能否跨家庭注入、能否无授权删除旧规则、对手是否被故意做弱、开发数字是否被包装成总体结论。封存集 seed 52001 起的 200 个家庭始终未执行。

## 第一轮：主动找漏洞

第一轮得到四个实质问题，初始实现不能直接进入封存测试。

### F1：权限签发者可伪造

旧边界只要求权限证明来自 `USER` 或 `IMPORT`，却没有可信签发者名单。攻击者只需构造一个格式正确的导入记录，就能把访客写成主人。

整改：决策入口必须传入 `trusted_issuer_ids`；有效权限证明必须由该集合中的 person/device 签发。不可信签发者的声明降为 `unverified_reporter`，并输出 `downgraded_untrusted_issuer` 回执。

### F2：决策没有显式家庭边界

偏好虽然带 `household_id`，解析器却没有把“本次是在谁家决策”作为硬输入。跨家庭记录有进入当前裁决的可能。

整改：增加必填 `decision_household_id`。不属于本家庭的偏好不参与裁决，并输出 `rejected_cross_household` 回执。

### F3：裸 `superseded=true` 可以删除规则

行动解析器直接相信记录上的“已被替代”布尔值。只要上游把主人偏好或硬安全规范标成已撤销，旧规则就会无声消失，现有更新权限策略无法补救。

整改：增加 `PlacementRetirementAuthorization`。撤销必须同时满足家庭一致、签发者可信、权限足够；硬安全规则还必须带显式安全移除确认。条件不满足时恢复旧记录为 active，并把 ID 写入 `refused_retirement_record_ids`。合法撤销写入 `authorized_retired_record_ids`。

### F4：直接对手和统计表述偏弱

原 collapsed 对手把不同身份完全等权相加；它没有利用自己可见的权限证明。30 个家庭又只是十个模板的确定性换 ID 版本，家庭 bootstrap 区间不能解释成对真实家庭总体的置信区间。

整改：collapsed 对手也验证权限来源，并使用冻结的连续权限权重；authority-agnostic 对手增加同层同时冲突检测。报告新增：

- `effective_structural_scenario_count=10`；
- `inference_validity=deterministic_fixture_variants_not_population_inference`；
- `confidence_intervals_valid_for_external_claim=false`。

## 第二轮：针对修复重新攻击

第二轮把原 11 类攻击扩展到 16 类，每类在 30 个开发家庭上执行，合计 480 个家庭级检查。

新增五类专门攻击：

1. 不可信设备签发“访客是主人”；
2. 其他家庭的偏好注入当前家庭；
3. 无撤销回执把主人偏好标为已替代；
4. 无安全确认回执把硬规范标为已替代；
5. 可信撤销回执正向控制，防止系统只会一律拒绝。

结果：16/16 类攻击均为 30/30 通过；候选 hard safety violation、unauthorized override、semantic layer violation 均为 0。封存测试访问次数为 0。

## 加强对手后的开发结果

两个对手都在 20 个 tuning 家庭上独立调参，再在另外 10 个 diagnostic 家庭、100 个 episode 上诊断。

| 方法 | 错误放置率 | 语义层违规率 | 越权覆盖率 | 硬安全违规率 |
|---|---:|---:|---:|---:|
| authority-scoped v0.2 | 0.00 | 0.00 | 0.00 | 0.00 |
| strengthened collapsed placement memory | 0.26 | 0.10 | 0.00 | 0.00 |
| strengthened authority-agnostic resolver | 0.30 | 0.30 | 0.30 | 0.00 |

这说明 v0.2 在当前十类人工机制题上没有被两个直接对手推翻；它不说明真实家庭中一定领先，也不说明这项机制已经构成论文创新。

## 第二轮仍不能消除的风险

- oracle（标准答案）仍由我们定义，真实用户在冲突时是否希望核验尚未验证；
- 家庭 seed 不是独立生活轨迹，只是确定性模板变体；
- 权限登记服务、身份识别错误、LLM 提取错误和真实感知噪声尚未进入闭环；
- collapsed 对手虽然加强，但还不是外部论文系统的忠实复现；
- `system_admin` 高于 household owner 的产品治理含义仍需单独决策，不能借本审核自动冻结；
- 封存集只应在候选实现、对手和代价表再次确认冻结后执行一次。

## 审核结论

代码层面可以说：第一轮发现的三个安全漏洞已封闭，第二轮专项攻击全部通过，增强对手后候选仍在开发机制题上领先。

研究层面只能说：该路线获得了进入一次性封存机制测试的资格。`paper_claim_allowed=false`、`formal_decision=not_evaluated` 保持不变；接真实数据、LLM、身份认证和外部系统前，不能把这里的 0.00 当成真实效果。
